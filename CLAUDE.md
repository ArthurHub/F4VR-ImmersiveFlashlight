# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project Overview

F4VR-ImmersiveFlashlight is a **C++23 DLL plugin** for F4SE (Fallout 4 Script Extender) that replaces the VR flashlight system. It supports 5 mounting positions (head, power-armor head, offhand, primary hand, weapon-mounted) with per-mode beam configuration (intensity, radius, FOV, color, gobo textures) and an in-game VR configuration UI. It also stows a beam-less flashlight model on the body that the player can physically grab to turn the light on into a hand (and put back to turn it off), a matching head-activation gesture that brings the offhand near the HMD to put the light on the head, and an offhand-near-primary-hand gesture that moves the light between the offhand and the primary hand / weapon. An optional headgear requirement can gate the head-mounted light (out of power armor) behind wearing any headgear, or specific "light-capable" headgear via a keyword + allow/deny rule. An optional weapon-flashlight requirement can gate the weapon-mounted light behind the equipped weapon actually carrying a modeled flashlight mesh, rooting the beam at that mesh.

## Build System

**Prerequisites:**

- `VCPKG_ROOT` environment variable pointing to a vcpkg installation
- Visual Studio 2022 or 2026 (MSVC toolchain, x64)
- Git submodules initialized: `git submodule update --init --recursive`

**Configure and build:**

```bash
cmake --preset default                                    # uses VS 2026; substitute vs2022 preset if needed
cmake --build --preset default --config Release
cmake --build --preset default --config Debug
```

The default preset inherits `cmake-dev + vcpkg + windows + vs2026`. The build output is `build/`. In-source builds are blocked.

**Auto-copy to game (optional):** Pass `-DPOST_BUILD_COPY_PLUGIN=ON -DCOPY_PLUGIN_BASE_PATH=<Fallout4VR_path>` during configure to copy the DLL and PDB to `<path>/F4SE/Plugins/` on each build. Multiple paths can be separated by `;`.

**Release packaging:** Release builds automatically run `cmake/package.cmake` to produce a `.7z` archive with the DLL and mod data files.

**No automated test suite** — testing is manual via in-game gameplay and the configuration UI.

## Architecture

### Plugin Lifecycle

The entry point is [src/FlashlightMod.h](src/FlashlightMod.h) / [src/FlashlightMod.cpp](src/FlashlightMod.cpp), a `ModBase` subclass that implements the F4SE plugin hooks:

- `F4SEPlugin_Query` / `F4SEPlugin_Load` — standard F4SE registration
- `onGameLoaded()` — creates `Flashlight` and `config::MainScreen` instances, loads config, registers the config button with FRIK, patches the mining helmet keyword, and resolves the restriction form lists (`RestrictionHandler::resolveForms()`)
- `onFrameUpdate()` — drives both the flashlight logic and config UI each frame

### Location Model

There are two related enums:

- `FlashlightLocation` — 5 runtime positions (Head, PAHead, OffHand, PrimaryHand, OnWeapon)
- `FlashlightConfigLocation` — 4 UI-facing positions (OnWeapon excluded from the config UI)

Config stores independent beam settings (fade, radius, FOV, RGB, gobo path, angle offset) for each location. `FlashlightState::setFlashlightRuntimeLocationOverride()` enables temporary override used during config UI preview.

The chosen `FlashlightConfigLocation` is tracked separately for out of / in power armor (`iFlashlightLocation` / `iFlashlightLocationInPA`). `FlashlightState::getActiveFlashlightConfigLocation()` picks the variant by `f4vr::isInPowerArmor()`, so `getFlashlightLocation()` resolves the runtime location against the right one and `switchFlashlightConfigLocation()` saves only the current state's value. Entering/exiting PA switches the location smoothly via the per-frame `refreshFlashlightLocation()`.

For config `InPrimaryHand`, `getFlashlightLocation()` resolves the runtime location by what's in the primary hand: an empty hand → `InPrimaryHand`, a drawn **regular (ranged) weapon** → `OnWeapon`, a drawn **melee weapon** → `InPrimaryHand` (the hand is occupied — the light can't sit there, so it is **not** relocated to the offhand; `RestrictionHandler::enforceRestrictions()` turns an on-melee primary-hand light **off**). `isMeleeWeaponEquipped()` is true only while the actor is actively wielding melee (drawn), so a sheathed melee weapon leaves the empty-hand resolution intact.

For config `InOffhand`, `getFlashlightLocation()` resolves to `InOffhand` normally, but a **two-handed grip** (`FRIKApi::isOffHandGrippingWeapon()`) occupies the offhand and routes the light to `OnWeapon`. When the **weapon-flashlight-mesh requirement** is effectively on (`RestrictionHandler::isWeaponFlashlightMeshRequired()`) and the weapon carries no modeled flashlight (`RestrictionHandler::isWeaponFlashlightAllowed()` false), it instead falls back to the **head** (`OnHead` / `OnPAHead`) rather than turning the light off, so the light isn't lost during a two-handed hold; releasing the grip resolves back to `InOffhand`. The head fallback is then itself subject to the headgear requirement (an unmet head requirement turns it off via `enforceRestrictions()`). With the requirement off, the offhand two-handed grip routes to `OnWeapon` unchanged.

### Grip Style

Hand-held locations (`InOffhand` / `InPrimaryHand`) have an additional `FlashlightGripStyle` dimension: `Forward` (thumb-up grip, controller top up) and `Overhand` (fist/ice-pick grip, controller flipped around its barrel so the top faces down while the light still points forward). `FlashlightState::refreshGripStyle()` runs each frame and picks the style from `Config::flashlightGripMode` — `Auto` measures the angle between the wand's local +Z and world up and applies hysteresis (`fFlashlightGripOverhandTiltDegrees` + `fFlashlightGripHysteresisDegrees`); `ForwardOnly` / `OverhandOnly` lock the style.

Each grip style has its own light transform (`tFlashlightIn{Offhand,PrimaryHand}Transform[Overhand]`), mesh transform (`tFlashlightMeshTransform[Overhand]`), and FRIK hand pose (`hFlashlightHandPose[Overhand]`). Light transform is re-resolved every frame; mesh transform and hand pose are re-applied by `FlashlightMesh` when the grip style changes mid-attach (no detach/reattach — same parent node).

The mesh transform and hand pose also have a power-armor variant (`...PA` suffix) because PA gauntlets are sized/posed differently than bare hands. `Config::getFlashlightMeshTransform()` and `getFlashlightHandPose()` select the PA or non-PA value by `f4vr::isInPowerArmor()`; each PA key defaults to its non-PA counterpart when omitted from the INI. The **light transform is not split** — `getFlashlightInHandLightTransform()` uses one value in and out of PA — and neither are beam values (fade/radius/FOV/color/gobo). On a PA transition the skeleton swaps, so `Flashlight::handlePowerArmorTransition()` calls `FlashlightMesh::invalidate()` to force a detach/reattach that re-resolves the PA transforms and pose.

### Body Stow & Grab

`Flashlight` owns the whole feature directly: a `BodyFlashlightMesh` (the stowed model) and a `WandActivationSphere` (the grab zone — handles the world-space test, owner-keyed button suppression, the entry haptic, and the debug visual), plus the post-toggle cooldown. `Flashlight::onFrameUpdate()` calls `updateBodyStow()` early (it reads the light state itself), then re-reads `isFlashlightOn()` because a grab/return may toggle the light mid-frame. Light mutations go through `Utils::`/`FlashlightState::` (`turnFlashlightOn`/`turnFlashlightOff` on `Utils`, `switchFlashlightConfigLocation` on `FlashlightState`), so no other class touches global flashlight state directly.

Each of the three spheres (body grab, head, primary-hand) is configured by a `f4vr::WandActivationConfig` bundle — `Config::bodyActivation` / `headActivation` / `primaryHandActivation` — loaded from its own `[ImFl_*ActivationSphere]` INI section via `ConfigBase::loadWandActivationConfig`: `tZone` (+ optional PA `tZonePA`, picked by `WandActivationConfig::zoneFor`), `sPrimaryBinding` / `sSecondaryBinding` (with per-binding `suppress` as a token in the binding string), an entry haptic (`sEntryHaptic`) + per-binding activation haptics (`sPrimaryHaptic` / `sSecondaryHaptic`), a 3-state visibility (`sShowSphere`: never / always / wheninside), the sphere's visual mesh (`sSphereNif` — empty = the framework default `debug-sphere.nif`; a per-sphere `.nif` path, swapped live on hot-reload), and a visual-only scale (`fSphereScale` — multiplies the drawn sphere's size but not the interaction radius, so `< 1` draws a smaller "hand is inside" hint within the real zone). See [the framework input-binding & activation-sphere docs](external/F4VR-CommonFramework/docs/input-binding.md#activation-spheres).

- **Stowed model:** `BodyFlashlightMesh` shows a beam-less clone on the chest bone except while the light is **held in a hand** (offhand / primary hand — the physical unit has left the body); an **off**, **head-mounted**, _or_ **weapon-mounted** light leaves the model stowed and visible (weapons carry their own flashlight mesh, and the in-hand `FlashlightMesh` shows only while on in a hand). It stays attached whenever the feature is enabled; only visibility flips. `Flashlight::handlePowerArmorTransition()` / `onGameSessionLoaded()` call `_bodyMesh.invalidate()` (+ `_grabSphere.detachDebug()`) on skeleton swaps.
- **Stow location:** the model attaches to the **chest** bone (`f4vr::SkellyBones::Chest`). The model transform (`tFlashlightBodyTransform` + `...PA`) and the grab-sphere transform (the `[ImFl_BodyActivationSphere]` section's `tZone` + optional `tZonePA`, in `Config::bodyActivation`) are authored for a right-handed player and auto-mirrored (Z translate + heading/roll) when the player is left-handed (`f4vr::isLeftHandedMode()`), so one value works for both handedness modes.
- **Grab zone (no mesh):** the zone lives in `Flashlight`'s `WandActivationSphere`, fed the parent bone (`BodyFlashlightMesh::attachedNode()`) and the zone transform (`BodyFlashlightMesh::grabZoneTransform()` — which offsets the grab translate by `tFlashlightBodyTransform`'s translate so the zone is measured **from the stowed model**, not the bone origin), Z-mirrored for left-handed players by `Flashlight` (`mirrorZoneIfNeeded`) **before** it is passed in — the sphere itself no longer mirrors. `WandActivationSphere::contains()` carries that into world space (the codebase's local→world convention from `MatrixUtils::calculateRelocation`) and `updateDebug()` places the debug sphere from the same inputs, so the visual and the test always agree. Only the model's _translate_ shifts the origin — its rotation/scale don't tilt or size the zone. The grab-sphere scale sizes the unit-**diameter** `debug-sphere.nif`, so the grab radius is `scale * boneWorldScale * SPHERE_NIF_BASE_RADIUS` (≈ half the scale). The global `bShowAllActivationSpheres` master (or this sphere's own 3-state `sShowSphere`: never/always/wheninside) loads/attaches that sphere mesh to visualize the exact zone for tuning; nothing is loaded when hidden.
- **Grab / return** (`Flashlight::checkBodyGrab()`): for each hand whose grab binding isn't `none`, while the wand is inside the grab zone its configured button is suppressed from the game/FRIK by the `WandActivationSphere` (owner key `ImFl_BodyGrab`, passed the per-hand `InputBinding`) and a one-shot entry haptic hints the zone. Firing the binding **returns** the light (turns it **off**) when it's already **held in that hand** (`isFlashlightOn && flashlightLocation == heldLocation`); otherwise it **grabs** — bringing the light to that hand from any other state (off → on, or head / the other hand → stays on, switches to that hand). A hand occupied by a **drawn weapon** can neither grab nor return — in practice this gates the primary hand (`isNodeVisible(getWeaponNode())`), since you can't take/stow the flashlight with the hand holding the gun/melee. A short post-toggle cooldown (`BODY_GRAB_COOLDOWN_MS`) prevents an immediate grab-then-return. The underlying `VRControllersSuppress` is auto-driven each frame by `ModBase`; suppression/release run on the main thread.

### Head Activation

`Flashlight::checkHeadActivation()` is the head-side analog of the body grab, driven from `onFrameUpdate()` right after the body grab — both run **before** the on/off early-return, so either may toggle the light first (the state is re-read afterwards). It has **no model**, only an activation zone (`Flashlight`'s second `WandActivationSphere`, `_headSphere`) and an optional debug sphere; light mutations go through `Utils::`/`FlashlightState::` like the body grab.

- **Offhand only.** Bringing the **offhand** wand into a sphere around the HMD suppresses its configured button via the `WandActivationSphere` (owner key `ImFl_HeadActivate`) and plays a one-shot entry haptic. The tap binding (`[ImFl_HeadActivationSphere] sPrimaryBinding`) puts the light **on the head**: on from off, switch-to-head from a hand, or **off** when already head-mounted. There is **no master on/off flag** — set the binding to `none` to disable. The turn-on path uses the same on-then-switch order as the body grab so the head beam values get refreshed.
- **Two offhand bindings, one sphere.** `sPrimaryBinding` (**default `offhand tap trigger`**) is the on/switch/off toggle above; `sSecondaryBinding` (**default `offhand longpress trigger`**, both in `[ImFl_HeadActivationSphere]`) pulls the **head-mounted** light to the offhand. Both feed the one `_headSphere`; the callback tells them apart by comparing the fired binding against the config value with `InputBinding`'s defaulted `operator==`. The long-press is fed as `DisabledBinding` unless the light is on and head-mounted, so the offhand button is suppressed (and the entry haptic fires) for it **only** when that gesture is available. Each binding's `none` disables its gesture.
- **Zone:** the same shared `WandActivationSphere`, fed the `[ImFl_HeadActivationSphere]` `tZone` carried into world space off `getPlayerNodes()->HmdNode` (no Z-mirror). It is **not** mirrored (centered on the head, so one value reads for both handedness) and has **no PA variant** (the HMD sits in the same place in/out of PA). `bShowAllActivationSpheres` — the **same** master flag as the body grab (or this sphere's own `sShowSphere`) — visualizes it; since the HMD node doesn't render its children, the debug sphere is parented to the rendered skeleton root (`f4vr::getRootNode()`, passed as `debugNode`) but relocated to the HMD-anchored zone center. Because the zone is centered on the HMD (translate `0,0,0`), the sphere surrounds the camera, so it's only visible from inside.

### Primary-Hand Activation

`Flashlight::checkPrimaryHandActivation()` is the offhand-near-primary-hand analog of head activation, driven from `onFrameUpdate()` right after it — also **before** the on/off early-return, because its on-weapon re-toggle turns the light back on from off (the state is re-read afterwards). It has **no model**, only an activation zone (`Flashlight`'s third `WandActivationSphere`, `_primaryHandSphere`) on the primary-hand wand node and an optional debug sphere; light mutations go through `Utils::`/`FlashlightState::` like the other interactions.

- **Zone:** the same shared `WandActivationSphere`, fed the `[ImFl_PrimaryHandActivationSphere]` `tZone` carried into world space off `getPrimaryHandWandNode()`. It is **not** mirrored (anchored to the hand node, so one value reads for both handedness) and has **no PA variant**. `bShowAllActivationSpheres` — the **same** master flag as the body grab/head zones (or this sphere's own `sShowSphere`) — visualizes it; since the wand node doesn't render its children, the debug sphere is parented to the rendered skeleton root (`f4vr::getRootNode()`, passed as `debugNode`) but relocated to the wand-anchored zone center. Note the zone is on the **primary hand** but the bindings are on the **offhand**, so `WandActivationSphere::isInsideZone` tests the offhand wand against the primary-hand zone.
  - **Anchor to the weapon flashlight mesh (optional):** when `bWeaponFlashlightAnchorPrimaryHandSphereToMesh` is on (default) and `RestrictionHandler::getOnWeaponFlashlightMeshNode()` returns a node, the sphere is anchored to that mesh node's **parent** (the offset to the lamp itself is carried in the zone transform) instead of the primary-hand wand, so the gesture is reached by bringing the offhand to the gun's lamp. Because that accessor is itself gated by `bWeaponFlashlightMountBeamToMesh` (it returns null when beam-to-mesh is off), the anchor follows the beam-rooting toggle — anchoring requires **both** flags on plus a detected lamp; otherwise it falls back to the wand node. The zone transform comes from the **mesh node's** own local transform plus the same mount offset that roots the beam, so only the **scale (radius)** is taken from the section's `tZone` — its translate/rotate are not read in this path. Uses the same node as the beam rooting.
- **Two offhand bindings, one sphere.** `sPrimaryBinding` (**default `offhand tap trigger`**) moves/toggles the light; `sSecondaryBinding` (**default `offhand longpress trigger`**, both in `[ImFl_PrimaryHandActivationSphere]`) only pulls the on-weapon light to the offhand. Both feed the one sphere; the callback tells them apart by comparing the fired binding against the config value with `InputBinding`'s defaulted `operator==`. Each binding is fed as `DisabledBinding` in states where it has no action, so the offhand button is suppressed (and the entry haptic fires) **only** when the gesture is actually available.
- **Tap rules** (all require the runtime location, which derives `OnWeapon` from config `InPrimaryHand` + a drawn regular weapon — see Location Model): light **on offhand** + primary hand empty → **primary hand**; + a drawn **regular weapon** → **on weapon**; + a **melee/unarmed** weapon → **inert** (button passes through). Light **on weapon** → toggle **off**. Light **on primary hand** → back to **offhand**. Light on head → inert. Light **off** (regardless of its stored location, like the head gesture turns it on from off) → turns **on at the primary hand** (empty) or **on the weapon** (regular weapon drawn); a **melee/unarmed** weapon is inert. Both "→ primary hand" and "→ on weapon" are the _same_ call (`switchFlashlightConfigLocation(InPrimaryHand)`); `FlashlightState::getFlashlightLocation()` resolves the empty / ranged-weapon / melee split (a drawn melee weapon resolves to `InPrimaryHand` and is then forced **off** by `RestrictionHandler::enforceRestrictions()` — see Location Model, so moving the light onto a melee-occupied hand turns it off rather than relocating it).

### Two-Handed Weapon Toggle

`Flashlight::checkWeaponFlashlightToggle()` is a **zone-less** offhand on/off toggle for the weapon-mounted light, for two-handed weapon holds where the offhand grips the foregrip and **can't reach the primary-hand sphere**. Driven from `onFrameUpdate()` right after `checkPrimaryHandActivation()` (so it can read this frame's sphere suppression) and **before** the on/off early-return (its turn-on works from off). No model, no zone — it reads the binding directly via `vrcf::VRControllers.check()`; light mutations go through `Utils::`/`FlashlightState::`.

- **Active only when:** the binding is enabled, FRIK reports the offhand is gripping the weapon (`frik::api::FRIKApi::inst->isOffHandGrippingWeapon()`), the runtime location is `OnWeapon`, `RestrictionHandler::isWeaponFlashlightAllowed()` is true, **and** no proximity zone is already claiming the same offhand input this frame (`_bodyGrabSphere`/`_headSphere`/`_primaryHandSphere` `isSuppressing(binding)`) — so a shared button (e.g. the default `offhand tap trigger`, same as the other gestures) isn't handled twice. Because the gating is `isOffHandGrippingWeapon()`, the one-handed weapon case is left to the primary-hand sphere (the free offhand can reach it).
- **One binding:** `sToggleWeaponFlashlightTwoHandedBinding` (**default `offhand tap trigger`**). A press toggles the weapon light **on ↔ off**; it does **not** switch the configured location (the location is already `OnWeapon`, resolved from config `InPrimaryHand` **or** config `InOffhand` + the two-handed grip — see Location Model — and the per-frame refresh applies the weapon beam values), so releasing the grip returns the light to whatever the config routes to. A success haptic fires on toggle.
- **Suppression (no zone):** while active, the bound button is suppressed under its own owner key (`ImFl_WeaponToggle`) so the game never sees the press. Since there is no `WandActivationSphere` to diff for it, `Flashlight` tracks the suppressed binding itself (`_weaponToggleSuppressedBinding`, an `std::optional<InputBinding>`) and issues suppress/release **only on edges** (matching the suppressor's act-on-changes contract). `onGameSessionLoaded()` clears it because the framework resets all suppression before that hook.

### Vanilla Toggle Disable

`bDisableVanillaFlashlightToggle` (default **on**) suppresses the game's built-in global flashlight (Pipboy light) toggle so only this mod's gestures control the light, applied through `Utils::setVanillaFlashlightToggleDisabled()`.

- **Mechanism:** disabling sets the `fPipboyLightDelay:Controls` game setting to `99` (an effectively unreachable long-press delay) after caching the original; re-enabling restores it. An `std::optional<bool>` tracks the applied state (`nullopt` = never applied) and the call **early-returns when the requested state already matches**, so it's idempotent.
- **When applied:** `Flashlight::onGameSessionLoaded()` applies the config value (first session load), and the config hot-reload subscriber re-applies it live so toggling the bool takes effect without a restart. INI settings persist at runtime across save loads, so the no-op guard is safe.

### Headgear Requirement (head restriction)

An optional gate on the head-mounted light, driven by `iFlashlightHeadgearRequirement` (`None` / `AnyHeadGear` / `Immersive`, see `FlashlightHeadgearRequirement`). It lives in **`RestrictionHandler`** (a static handler shared with the weapon restriction below) and applies **only out of power armor** — `RestrictionHandler::isHeadFlashlightAllowed()` returns `true` in PA (the helmet lamp always applies), and the PA head resolves to `OnPAHead`, not `OnHead`. The worn-headgear read mirrors `f4vr::isInPowerArmor()`: `getWornHeadgear()` reads `player->biped->object[0].parent.object` (slot 30 / biped index 0 = `kHairTop`, where hats/helmets sit), filtered to an `ARMO`.

- **Modes:** `None` always allows; `AnyHeadGear` requires any slot-30 headgear; `Immersive` requires _light-capable_ headgear via the rule `worn && !deny(formID) && ( allow(formID) || hasAnyKeyword(item, keywords) )` (`isLightCapableHeadgearWorn()`).
- **Immersive lists** (`sHeadLightKeywords`, `sHeadLightAllowList`, `sHeadLightDenyList`): `Config` parses them (keyword **editor IDs**; allow/deny as `localFormID|plugin` pairs) and `RestrictionHandler::resolveForms()` resolves them to runtime FormIDs once — called from `FlashlightMod::onGameLoaded()` and re-run on config hot-reload. Keywords resolve by scanning `TESDataHandler::GetFormArray<RE::BGSKeyword>()` and matching `BGSKeyword::formEditorID` (keyword editor IDs are retained at runtime); allow/deny resolve load-order-independently via `TESDataHandler::LookupForm(localID, plugin)`, so entries for absent plugins are simply skipped. Seed defaults ship the article's curated base-game + DLC set; the deny list wins over the allow list, which wins over the keyword set.
- **Enforcement when blocked → light off** (the chosen behavior): `Flashlight::checkHeadActivation()` gates its tap binding (`headTapActive`) so the put-on-head gesture is inert when the head isn't allowed (button passes through, no entry haptic), while still letting a head-mounted light be toggled off; and `RestrictionHandler::enforceRestrictions()` — run in `onFrameUpdate()` right after `refreshFlashlightLocation()` — turns an on-head light **off** when the requirement is no longer met (e.g. the helmet was removed). It mutates the light only through `Utils::`/`FlashlightState::`, and is skipped while a config-mode location override is active (`FlashlightState::isRuntimeLocationOverrideActive()`) so head beam tuning isn't interrupted.

### Weapon-Flashlight Requirement (weapon restriction)

An optional gate on the weapon-mounted light, driven by the 3-state `iWeaponFlashlightMeshRequired` (`FlashlightWeaponMeshRequirement`: `Disabled` / `Enabled` / `AutoDetect`; default `AutoDetect` in the shipped INI, code default `Disabled`). Also in **`RestrictionHandler`**, it requires the equipped weapon to actually carry a modeled flashlight mesh before the light may sit on it (`FlashlightLocation::OnWeapon`), and roots the beam at that mesh. `AutoDetect` turns the requirement on only when a supported weapon mod (`sWeaponFlashlightAutoDetectPlugins`, default `VRCP_DOOMMerged.esp` / `TacticalMods.esp`) is in the load order; the enum is resolved to an effective on/off bool once in `resolveForms()` (re-run on reload / `invalidate()`) and read everywhere via `RestrictionHandler::isWeaponFlashlightMeshRequired()`. Applies in **and** out of power armor (the gun is the same either way). Built per the reference library's `weapon_flashlight_detection.md` (Strategy B — scene-node-by-name, which doubles as both the yes/no detector and the mount anchor).

- **Detection (`RestrictionHandler::onFrameUpdate()` → `checkWeaponChangeForFlashlightOnWeaponDetection()`):** a cheap no-op while the requirement is off. Otherwise equipped-weapon tracking (drawn weapon, melee/unarmed flag, power-armor state) is delegated to the framework's `f4vr::EquippedWeaponHandler` (held as the `_weaponHandler` member, driven via `detectChange()`); **only when it reports a change** (and the weapon node is present and visible) does it walk the weapon 3D (`f4vr::findAVObject` under `getWeaponNode()`) for the first node whose name is in `sWeaponFlashlightMeshNodes` (config order = priority), caching that found node alongside the handler's weapon state; a holstered/unequipped weapon clears the node. The recursive walk is amortized to once per weapon change — there is **no rescan/grace window**, so a lamp whose 3D attaches a frame later isn't picked up until the next weapon change. Returns **whether the weapon changed**, so `Flashlight::onFrameUpdate()` can `invalidate()` the `OnWeaponBeamMesh`. Called each frame from `Flashlight::onFrameUpdate()` right before `enforceRestrictions()`.
- **Cache lifecycle:** `RestrictionHandler::invalidate()` resets the `_weaponHandler` (`EquippedWeaponHandler::invalidate()`) and drops the cached (potentially dangling) node, then re-runs `resolveForms()`, forcing a re-scan. Called from `FlashlightMod::onGameLoaded()`, `Flashlight::onGameSessionLoaded()` (weapon 3D rebuilt on save load), `Flashlight::handlePowerArmorTransition()` (the skeleton swap rebuilds the weapon 3D — also re-attaches `OnWeaponBeamMesh`), the config hot-reload subscriber, and the in-game requirement toggle (`Config::setWeaponFlashlightMeshRequirement` callers — the requirement may have flipped or the node list changed). Detection itself keys only on the equipped weapon (no power-armor key), so outside those `invalidate()` points the cached node is refreshed only when the weapon next changes. The node-name list is **NIF node names** (not ADDN editor IDs) — not contractual, verify in NifSkope; defaults cover Tactical Weapon Mods' `Gunlamp*` variants.
- **Beam rooting:** gated by `bWeaponFlashlightMountBeamToMesh` (default on) — `RestrictionHandler::getOnWeaponFlashlightMeshNode()` returns the detected mesh node (`.first`) only when that toggle is on, else null. When non-null, `Flashlight::adjustFlashlightTransformToHandOrHead()` roots the light at that mesh node via `calculateRelocation` with the configured `tWeaponFlashlightMountTransform` offset (not split by PA — it's relative to the lamp node) instead of the generic tuned barrel offset. When the toggle (or the requirement) is off, the accessor returns null and the generic mount is used. The same node is the optional anchor for the primary-hand activation sphere (`bWeaponFlashlightAnchorPrimaryHandSphereToMesh` — see Primary-Hand Activation).
- **Beam-only model on the weapon (`OnWeaponBeamMesh`):** because the rooted light has no visible glow at the gun's lamp, `Flashlight` also attaches the beam-only model (`flashlight-beam-only.nif`) as a child of the same mesh node's parent (`RestrictionHandler::getOnWeaponFlashlightMeshNode()`) with the same `tWeaponFlashlightMountTransform`, shown only while the light is on at `OnWeapon` and that node is non-null, so the lamp emits a tracking beam glow. Detached/hidden otherwise (and re-applied each frame for live-reload). See the **OnWeaponBeamMesh** component row.
- **Enforcement when missing → light off:** `RestrictionHandler::enforceRestrictions()` turns an on-weapon light **off** when the requirement is on, a weapon is equipped (`_weaponHandler.isDrawn()`), the location is `OnWeapon`, and `isWeaponFlashlightAllowed()` is false (no detected mesh) — the same chosen behavior as the headgear gate, via `Utils::`/`FlashlightState::`. Exception: a light routed to the weapon from config `InOffhand` by a **two-handed grip** never reaches `OnWeapon` when the weapon lacks a flashlight — `getFlashlightLocation()` sends it to the **head** instead (see Location Model), so `enforceRestrictions()`'s on-weapon branch only fires for the config `InPrimaryHand` / primary-hand weapon path.

### NPC Light Detection

An optional (default-on) gameplay feature making NPCs react to the beam, since vanilla detection ignores player spot lights entirely. `NpcDetectionHandler::onFrameUpdate()` (called from `Flashlight::onFrameUpdate()` after the light transform is applied, so it sees the same beam the player sees — including weapon-lamp rooting) runs a throttled tick (`runDetectionTick()`) that posts a single player-owned detection event at what the beam touches: near the nearest line-of-sight-visible NPC inside the beam cone (offset toward the player by 25% of the NPC→player distance, clamped to [150, 1000] units, so the NPC investigates toward the light source), or on the beam's lit spot on world geometry when nobody is in the cone. The two paths are separately gated by `bNpcDetectionDirectEnabled` / `bNpcDetectionLitSpotEnabled` (both default on), so either can be turned off to isolate the other for debugging without losing its tuned sound level. Sound levels (`iNpcDetectionDirectSoundLevel` / `iNpcDetectionLitSpotSoundLevel`) scale with the beam's strength at the target (distance falloff over the location's full visual radius × its fade, clamped), so per-location beam character stays meaningful; `fNpcDetectionMaxRange` caps eligibility reach independently of the visual radius and `fNpcDetectionFovMult` narrows the cone to the bright core. No hooks, no ESP — engine surface is `ProcessLists::GetActorsWithinRangeOfPoint` + `CombatUtilities::CalculateProjectileLOS` + `AIProcess::SetActorsDetectionEvent` (VR addresses cited in [docs/tech/npc-light-detection.md](docs/tech/npc-light-detection.md), which also documents the design trade-offs and the light node's +X beam-axis derivation). Skipped during config-UI beam preview, optionally sneak-only (`bNpcDetectionOnlyWhenSneaking`), companions ignored by default.

- **Debug overlay (gated by the framework's `bDebugDrawEnabled`, default on):** `drawDebugOverlay()` renders the live detection state each frame via the framework's `f4cf::debug` draw overlay (channel `NPC-DETECTION`): the detection cone (yellow, narrower/shorter than the visual beam by design), the last tick's event as a sphere + world-anchored sound-level label (red = direct on an NPC, with a magenta line/point to the lit NPC; orange = lit-spot on geometry; shown for a few ticks), and the watch table (framework default HUD in front of the HMD): `npc why` (**why the last tick did/didn't post** — `no npc in cone` / `N in cone, no LOS` / `beam in open air` / `direct off` / `lit-spot off` / `hit npc … lvl N`), next-tick countdown, cone range/FOV, and last-event summary. The last event + the tick reason/cone-count are kept in `_debugEvent` / `_debugReason` / `_debugConeCount` purely to feed this (the tick is throttled; the overlay draws every frame). Immediate-mode, so it vanishes with the light/feature; the overlay's own `[Debug]` keys (`bDebugDrawEnabled`, `sDebugDrawDisabledChannels`) gate it globally — see the framework's `src/debug/README.md` and `docs/tech/debug-draw-overlay.md`.

INI-only for now (hot-reload applies live) — a `MiscScreen` toggle needs a button NIF asset.

### Config Hot-Reload

`Config` subscribes to `thomasmonkman-filewatch` change events on the INI file. Changes made externally while the game is running are automatically applied without restart via `refreshFlashlightLocation()` / `setLightValues()`.

### Key INI File

[data/config/ImmersiveFlashlightVR.ini](data/config/ImmersiveFlashlightVR.ini) — the bundled default config. Deployed to the game directory; editable by users. Organized into two tiers: the main `[ImmersiveFlashlightVR]` section holds the common settings (location, per-mount beam appearance incl. the head light-node tilt, the global light properties `fFlashlightNearDistance` / `sFlashlightFlagsBitmask` / `bWarnAboutFPSStabilizerMod`, and the global toggles `bDisableVanillaFlashlightToggle` / `bShowAllActivationSpheres`); the advanced per-feature settings live in their own named `[ImFl_*]` sections — `[ImFl_HandMount]` (in-hand light/mesh transforms, hand poses, grip detection), `[ImFl_HeadgearRestriction]`, `[ImFl_WeaponMount]` (incl. `sToggleWeaponFlashlightTwoHandedBinding`), `[ImFl_BodyStow]`, `[ImFl_NpcDetection]`, and the three `[ImFl_*ActivationSphere]` sections. Section `[Debug]` controls log level. The section each key is read from is the section constant it's passed in [Config.cpp](src/Config.cpp)'s `loadIniConfigInternal` (`DEFAULT_SECTION` vs the `SECTION_*` constants); a moved key needs the same section in both its read and its `set*` write path. The `iVersion` bump (currently 15, in `[Debug]`) drives `ConfigBase`'s version migration, which rewrites an existing user's INI into the shipped layout, carrying forward values that still match by section+key — so relocating a key to a new section resets it to default for existing users (accepted; no custom remap).
